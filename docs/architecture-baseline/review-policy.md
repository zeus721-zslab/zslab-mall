# 검토 정책 — 위험도 등급과 외부 검토

> 이 문서는 정책 서술이며 결정 기록이 아니다. 개별 결정과 검토 결과는 [decisions.md](decisions.md)·[decisions-fe.md](decisions-fe.md)에 남는다. README "개발 방식"의 원본이다.

## 1. 등급

변경마다 정찰 단계에서 등급을 매긴다. 한 PR에 여러 트랙이 섞이면 가장 높은 등급을 적용한다.

| 등급 | 대상 | 외부 검토 |
|---|---|---|
| **A 필수** | **돈**: 결제·환불·정산·금액 계산<br>**재고·동시성**: 락·조건부 UPDATE·트랜잭션 경계·이벤트 동기/비동기 전환<br>**상태기계**: 전이 추가·예외·종결 조건<br>**데이터**: Flyway 컬럼 삭제·타입 변경·NOT NULL·백필, 운영 데이터 보정 SQL<br>**보안**: 인증·인가·권한 경계·파일 업로드·서빙·웹훅<br>**스케줄러**: 운영 데이터를 자동으로 바꾸는 배치 | 외부 검토 없이 머지하지 않는다 |
| **B 선택** | 조회 API·응답 필드 추가 · 추가형 Flyway(nullable 컬럼·인덱스) · 기존 로직을 재사용하는 신규 API · 실패해도 본 처리에 영향이 없는 부가 기능 | 필요 여부를 판단해 정하고, 생략하면 근거를 남긴다 |
| **C 생략** | FE 전용(BE 계약 무변경) · 문서 · CI·인프라 설정 · 테스트만 변경 | 생략 |

## 2. 절차

1. 구현·자체 검증(영향 테스트 → 커밋 직전 전체 테스트)
2. (A·B) 셀프 리뷰 — 변경 diff를 별도 서브에이전트가 리뷰하고, 지적마다 수용·기각을 판정한다. A 등급은 셀프 리뷰로 외부 검토를 대신하지 않는다.
3. 외부 검토(A 필수 · B 선택)
4. 반영
5. 커밋·PR
6. 머지

## 3. 외부 검토자

- OpenAI ChatGPT를 쓴다. 구현은 Claude 기반 에이전트가 하므로 다른 회사의 모델에 맡겨 같은 모델이 공유하는 사각지대를 피한다.
- 웹 UI에서 라운드마다 새 채팅을 열어, 프로젝트 맥락이 없는 독립 리뷰어로 운용한다. 판단 근거는 투입한 패킷 안에 있어야 한다.

## 4. 패킷

- 저장소 밖 검토 폴더에 둔다: 투입 문구 + 자기완결 `.md` 파트.
- 파트 구성: 라운드의 첫 파트 머리에 요청문(배경 · 이 라운드 범위 · 결정 요지 · 집중 질문 3~7개 · 응답 형식 · 알려진 이월) · 이어서 diff 발췌와 테스트 요지.
- 분량: 파트당 20KB(바이트) 이하 · 라운드당 5파트 이하 · 2라운드(최대 10파트) 이내. 넘으면 싣는 대상을 좁히고, 그래도 넘으면 PR 분할 신호로 본다.
- `.java` 원문을 통째로 첨부하지 않는다 — 변경 hunk와 판단에 필요한 핵심 구간만 발췌한다. 변경 판단에 필요한 무변경 대조 자료는 "대조용 · 무변경"으로 표시해 싣는다.

## 5. 판정

- 지적 항목마다 수용 또는 기각으로 판정한다. 기각은 근거 1줄을 붙인다.
- 수용한 항목은 같은 브랜치에서 반영한 뒤 머지한다.

## 6. 재검토

- 반영이 설계 변경(새 구조·새 경로·트랜잭션 경계 이동)이면 1회 재검토한다.
- 국소 수정이면 지적된 시나리오를 테스트로 재현·통과시키는 것으로 끝낸다.
- 연속 재검토는 최대 2회로 한다.

## 7. 기록

- 해당 결정 끝에 1줄을 append한다: `외부 검토: 등급 / 지적 N건 중 수용 N건`. 생략했다면 `외부 검토: B / 생략(근거)` · `외부 검토: C / 생략`.

## 8. 코드 외 검토

- 코드가 아닌 설계도 같은 방식으로 검토받는다. 예: 최종 점검의 주문 시나리오 설계를 이커머스 QA 리뷰어 역할로 외부 검토받은 뒤 시뮬레이션을 돌렸다(그 결과로 나온 크리티컬 처리가 D-255).

## 9. 적용 시점 주의

- 등급제 도입 이전 결정에는 등급 표기가 없거나 형식이 다를 수 있다. `외부 검토: A / 지적 N건 중 수용 N건` 형식의 첫 기록은 D-172다.
